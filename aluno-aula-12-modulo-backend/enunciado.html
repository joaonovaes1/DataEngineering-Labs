Exercício 03 — refatorar em módulo, com plan limpo

O único exercício do semestre que não constrói nada novo. Você reorganiza o código e move o estado — sem recriar um único recurso. Rode o verifica.sh antes de entregar.

Pegue a stack plana do ponto de partida (o seu Exercício 02, numa forma canônica) e transforme-a em módulo + backend remoto + workspace, com uma regra dura: o terraform plan no fim tem que dizer “No changes”. Mesma infraestrutura, código diferente, zero recurso recriado.
Por que isso é diferente

Construir do zero é fácil de provar: o recurso existe ou não. Refatorar é traiçoeiro: embrulhar a stack num módulo muda o endereço de cada recurso no estado, e o Terraform, se você deixar, destrói e recria tudo para "consertar" a diferença. O ofício aqui é mudar o código sem que a AWS perceba. A ferramenta é terraform state mv, e a prova é o plan limpo.

Tempo: 90 min, em aula
Região: us-east-1
Custo teto: US$ 1,00
Backend: o compartilhado (não deste exercício)
Entrega: PR ao fim da aula
Vale: a stack "módulo + backend + workspace" da AV1

Passo a passo

Os comandos estão completos. A ordem é a lição: mover o estado antes de aplicar.

1

Prepare o ambiente

Digite (troque seulogin; só minúsculas e números, sem hífen)
export AWS_REGION=us-east-1
export SUFIXO=seulogin
cd terraform
cp terraform.tfvars.example terraform.tfvars   # e preencha sufixo
Confira que o backend da disciplina está de pé: aws s3 ls s3://eda-tfstate-$SUFIXO e aws dynamodb describe-table --table-name eda-tflock. Ele não é deste exercício — só o usamos.
2

Suba a stack plana (o ponto de partida)

Digite e confirme com yes
terraform init
terraform apply -var="sufixo=$SUFIXO"
Você deve ver
Apply complete! Resources: 6 added.
São seis recursos, todos na raiz, estado local. É o que você vai refatorar — sem recriá-los.
3

Refatore o CÓDIGO em módulo (DECISÃO 01)

  • Crie a pasta modules/lake/ com main.tf, variables.tf, outputs.tf.
  • Mova os seis blocos resource da raiz para modules/lake/main.tf — sem mudar nada dentro deles (mesmos nomes, mesmas propriedades).
  • Na raiz, troque os seis blocos por um só: module "lake" { source = "./modules/lake" sufixo = var.sufixo teto_bytes = var.teto_bytes }.
  • Preserve os cinco outputs, agora lendo do módulo (module.lake.bucket_name).
Regra de ouro: se você mudar o nome de um recurso, ele deixa de casar com o que existe e vira recriação. Refatorar é reorganizar, não rebatizar.
4

Veja o problema — dê um plan AGORA (o momento “aha”)

Digite
terraform plan -var="sufixo=$SUFIXO"
Você deve ver o Terraform querendo DESTRUIR e RECRIAR tudo
Plan: 6 to add, 0 to change, 6 to destroy.
Por quê? O código agora fala de module.lake.aws_s3_bucket.lake, mas o estado ainda guarda aws_s3_bucket.lake. Para o Terraform, o primeiro sumiu e o segundo apareceu — então ele quer apagar e criar. Não aplique. O próximo passo conserta isso.
5

Mova o ESTADO — terraform state mv (DECISÃO 02)

Digite (um por recurso — muda o endereço no estado, não a AWS)
terraform state mv aws_s3_bucket.lake                     module.lake.aws_s3_bucket.lake
terraform state mv aws_s3_bucket_public_access_block.lake module.lake.aws_s3_bucket_public_access_block.lake
terraform state mv aws_s3_bucket.results                  module.lake.aws_s3_bucket.results
terraform state mv aws_glue_catalog_database.db           module.lake.aws_glue_catalog_database.db
terraform state mv aws_glue_catalog_table.corridas        module.lake.aws_glue_catalog_table.corridas
terraform state mv aws_athena_workgroup.wg                module.lake.aws_athena_workgroup.wg
Você deve ver, seis vezes
Successfully moved 1 object(s).
Cada state mv diz ao Terraform: "esse recurso não sumiu — ele só mudou de endereço no seu mapa". Nenhuma chamada à AWS acontece.
6

Prove que não recriou (plan limpo, ainda local)

Digite
terraform plan -var="sufixo=$SUFIXO"
Você deve ver
No changes. Your infrastructure matches the configuration.
Metade do exercício, feita. O código está em módulo e o plan está limpo — você reorganizou sem recriar. Falta levar o estado para o backend remoto.
7

Migre o estado para o backend remoto

Digite (crie o backend.hcl e migre)
cat > backend.hcl <<EOF
bucket         = "eda-tfstate-$SUFIXO"
key            = "aula12/terraform.tfstate"
region         = "us-east-1"
dynamodb_table = "eda-tflock"
encrypt        = true
EOF
Adicione o bloco backend em um arquivo (ex.: backend.tf) e rode
terraform init -migrate-state -backend-config=backend.hcl
Adicione ao seu código: terraform { backend "s3" { workspace_key_prefix = "eda-a12" } }. O init -migrate-state pergunta se copia o estado local para o S3 — responda yes.
8

Prove de novo — plan limpo, agora remoto

Digite
terraform plan -var="sufixo=$SUFIXO"
Você deve ver
No changes.
O estado está no S3 e o plan continua limpo: a migração de backend também não recriou nada.
9

Use um workspace (DECISÃO 03)

Digite
terraform workspace new dev
terraform workspace select default
Seu backend já separa o estado por workspace (workspace_key_prefix). A stack migrada fica no workspace default: renomeá-la para dev mudaria os nomes dos recursos e recriaria tudo — que é o que este exercício proíbe. Workspace novo é para ambiente novo. Justifique essa escolha no DECISOES.md.
10

Rode a verificação

Digite
cd ../verificacao && ./verifica.sh
O critério 1 (o plan limpo) vale 30% — é o coração. Se ele falhar, você recriou algo: revise o Passo 5 (faltou um state mv?) ou o Passo 3 (mudou um nome?).
11

Escreva o DECISOES.md

Uma frase por decisão (01 a 05). Fale da refatoração, não do lake: a fronteira do módulo, como você moveu o estado, workspace × pasta, o que o plan limpo prova (e o que não prova), e o que quebraria se você tivesse aplicado antes do state mv.

12

Derrube e prove limpo, depois abra o PR

Digite
cd ../terraform && terraform destroy -var="sufixo=$SUFIXO"
cd ../verificacao && ./verifica.sh --pos-destroy
PR com a pasta refatorada, o DECISOES.md e a saída do verifica.sh colada. Não comite terraform.tfstate, .terraform/ nem backend.hcl com o nome da conta.

O critério 1 é o exercício. Um plan que quer mudar qualquer coisa significa que você recriou algo — e refatorar que recria não é refatorar.

Checkpoints

  • 20 min — stack plana aplicada e código já em módulo (Passo 3).
  • 40 min — plan limpo depois do state mv (Passo 6).
  • 75 min — estado no backend, verifica.sh verde e PR aberto.

O que mais reprova

  • Aplicar antes do state mv — destrói e recria; às vezes deixa a stack meio quebrada.
  • Mudar o nome de um recurso ao movê-lo para o módulo — vira recriação, e o plan não fica limpo.
  • Esquecer um state mv — sobra um recurso "órfão" no plan.
  • Comitar terraform.tfstate ou backend.hcl com o nome da conta.
